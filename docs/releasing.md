# Публикация Miracle

Приложение поставляется для macOS Apple Silicon (ARM64) и GNU/Linux ARM64/x64 с Node.js и SQLite. Windows поддерживается через WSL 2 и те же Linux-архивы. Docker-образ и PostgreSQL не входят в пользовательскую установку.

## Подготовка

Текущий опубликованный стабильный выпуск — **0.11.1**: [результаты проверки](release-validation.md). Он добавляет поддержку beta-канала в установщике и CLI; DuckDB остаётся в отдельном предварительном выпуске 0.12.0-beta.1. Для следующего выпуска сначала выберите новый номер версии; не переиспользуйте опубликованный тег. До публикации сохраняйте публичную ссылку на последний доступный выпуск. Перед сборкой обновите предыдущую поддерживаемую версию в `.github/workflows/checks.yml` и `tests/upgrade-smoke.mjs`, затем сверьте основную ветку с remote, версии в `package.json` / `package-lock.json`, заметки выпуска и список проверок в `release-validation.md`. Примеры ниже воспроизводят сборку 0.11.1 и её обновление с 0.11.0; для нового выпуска замените обе версии.

```sh
npm ci
npm test
npm run build
npm run notices
node scripts/build-release.mjs Manannikov-Nikita/miracle 0.11.1 .local/releases darwin-arm64
```

Параметры сборщика: repository, version, output, target и необязательный путь к заранее скачанному архиву Node. Три target: darwin-arm64, linux-arm64, linux-x64. Используется фиксированный Node 24.22.2, архив runtime проверяется по SHA-256. Все три архива поставляются в `.tar.gz`; рядом с каждым публикуется файл `.sha256`.

Сборщик включает только compiled client/server, production-зависимости, runtime, launcher и лицензии. Рабочая директория целиком не архивируется. .local, базы, ключи, env и личные данные не должны попадать в payload.

## Проверка артефактов

Сборка исходников не подтверждает работу установщика. На нативных runners проверяются архивы каждой поддерживаемой платформы: запуск bundled runtime без системного Node, произвольный cwd, пробелы/Unicode в пути, start/status/stop, повторный запуск, занятый порт, установка/повторная установка, контрольные суммы и сохранность данных.

Отдельно проверяются SQLite-ключ, отказ второй копии, crash recovery, backup/restore в пустую область. Реальные ClickHouse/Trino и TLS интеграции запускаются с их тестовыми источниками.

Обязательно проверьте обновление с предыдущего поддерживаемого выпуска через встроенный `miracle update`. CI скачивает опубликованный архив 0.11.0 и проверяет переход на кандидата: проверку доступности без остановки процесса, отклонение неверной контрольной суммы, сохранение данных и ключей, нестандартных путей, повторное обновление на уже актуальной версии. Выпуски без встроенного обновления не поддерживаются и не участвуют в CI.

```sh
node tests/upgrade-smoke.mjs \
  .local/releases/miracle-0.11.1-darwin-arm64.tar.gz \
  .local/previous-release/miracle-0.11.0-darwin-arm64.tar.gz
```

Рядом с архивами должны быть их `.sha256` и `install.sh`. Для других runners замените target в именах архивов. Перед публикацией транспорт теста подставляет локальные файлы в официальный путь обновления; после публикации отдельно проверяется настоящий сетевой переход через GitHub Release.

Новый `miracle update --check` не должен менять установку или останавливать проекты. `miracle update` должен использовать официальный стабильный выпуск и исходные каталоги установки/launcher; `--to X.Y.Z` выбирает фиксированную опубликованную версию. Проверьте отсутствие обновления при ошибке загрузки или контрольной суммы, отказ от понижения версии и повторное обновление на уже установленную версию. При проверке кандидата используйте его локальные архивы, не публикуйте тестовые assets вместо существующих.

Импорт старых SQL-черновиков проверяется отдельно в браузере на исходном origin. Установочный тест SQLite сам по себе не подтверждает перенос localStorage из браузера. После импорта проверьте backup/restore в `.miracle/` выбранного проекта.

Не называйте CI пройденным до фактического запуска workflow. Локальная macOS-проверка не заменяет Linux CI. Проверку сети WSL 2 и открытия адреса в браузере Windows фиксируйте отдельно: обычный Linux runner её не выполняет. Проверка на реальном WSL-хосте пока не выполнялась. Результаты фиксируются в [release-validation.md](release-validation.md).

## Публикация

Подготовка кандидата не создаёт тег и не запускает публикацию. После отдельного решения о выпуске и проверки исходников/артефактов создайте новый тег vX.Y.Z. Release workflow публикует три архива macOS/Linux, их SHA-256 и `install.sh` из того же выпуска. Версия внутри bootstrap-скрипта фиксирована, поэтому последующие скачивания относятся к одному тегу.

Не переназначайте опубликованный тег и не заменяйте его файлы другим содержимым. Для исправления нужен новый выпуск. Локальная сборка ничего не публикует.

Установщик `releases/latest/download/install.sh` доступен только после публикации этого asset. Не обещайте установку новой версии до появления её файлов в GitHub Release. Выпуск 0.1.0 относится к прежней Docker-поставке и не содержит native-архивов.

После выпуска проверьте скачивание без авторизации, SHA-256, чистую установку и переход с предыдущего поддерживаемого выпуска через `miracle update`. Проверьте также `miracle update --check` и обновление через официальный GitHub Release. Только затем обновите ссылку на выпуск в README и добавьте подтверждённые результаты проверки.
