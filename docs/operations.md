# Miracle operations

Miracle stores accounts, encrypted connection credentials, sessions, query history, snapshots and boards in PostgreSQL 17. ClickHouse and Trino are external analytical sources. The bundled test profile has only synthetic data and is not production infrastructure.

## Local development

Use Node 24. Run `npm ci`, `node scripts/init-local.mjs`, then `docker compose --profile test up -d --wait postgres clickhouse trino`. These services bind only to loopback at PostgreSQL 5544, ClickHouse 18123, Trino 18080. No existing service on 5432 or 5173 is used or stopped. Copy `.env.example` to `.local/runtime.env`, then export the variables from that file before starting the API. With Node 24 you can use `node --env-file=.local/runtime.env --import tsx src/server/index.ts`; start the frontend with `npm run dev:web` on 5178.

Create the first admin with `npm run bootstrap-admin`; the CLI accepts `MIRACLE_ADMIN_EMAIL`, `MIRACLE_ADMIN_NAME`, `MIRACLE_ADMIN_PASSWORD` from the environment. Prefer its interactive password prompt or a mode-0600 local env file instead of a password in shell arguments. Invitations are closed, generated by an administrator. The activation link must be delivered privately. No example admin account is installed automatically.

Test connections:

- ClickHouse URL `http://127.0.0.1:18123`, username `miracle_reader`, password `miracle_reader_local`, database `demo`. `demo.sales` and `demo.events` are synthetic fixtures. Readonly=1 is enforced by the ClickHouse user profile with explicit SELECT-only grants on demo tables and two metadata tables. Bounded changeable_in_readonly constraints permit per-query limits without allowing writes or BACKUP.
- Trino URL `http://127.0.0.1:18080`, username `miracle_reader`, catalog `tpch`, schema `tiny`, no password. Trino file access control allows this user read-only catalog access. TPC-H is generated data. The local HTTP server has no authentication; never expose it publicly.

From the Compose app container the hosts are `http://clickhouse:8123` and `http://trino:8080`. In production, provision dedicated read-only database users and firewall the analytical engines; the app's SQL validation is an additional boundary, not a replacement for engine permissions.

Run `npm test`, `npm run build`, and `npm run test:integration`. Integration creates its own disposable PostgreSQL database, invokes real HTTP routes and actual analytical engines, then removes only that database. It checks activation, roles, CSRF, credential redaction, schemas, precision-sensitive types, saved queries, board revisions, pinned refresh including failed refresh preservation, mutation rejection, time/row/byte/concurrency/chart/storage limits, cancellation, restart durability, 15,000 Trino rows and a real backup/restore rehearsal.

## Production installation

Run exactly one API process per workspace database. Startup marks unfinished runs interrupted; a second API against the same database could invalidate the first process's active runs. Image smoke and integration scripts use separate databases for this reason.

1. Set a strong `POSTGRES_PASSWORD` in a protected env file. Its URL encoding must be valid inside `DATABASE_URL`; use a long alphanumeric generated password or URL-encode reserved characters. Keep this file outside version control.
2. Generate the encryption key once with `node scripts/init-local.mjs`. Back up `.local/encryption.key` securely and independently of the database. Keep the exact same key through rebuilds and upgrades. Losing it makes saved credentials undecryptable; rotating it without re-encryption is unsupported.
3. Set `APP_ORIGIN` to the exact HTTPS origin and `COOKIE_SECURE=true`. Terminate HTTPS at your reverse proxy and proxy all paths to port 3001. The API and built frontend share one origin. Compose binds port 3001 only to loopback. For plain HTTP local checks explicitly set `COOKIE_SECURE=false`.
4. Run `docker compose --env-file .local/production.env --profile app up -d --build --wait`. The container entrypoint reads the mode-0600 file secret, then permanently drops root privileges to UID/GID 1000 before importing the HTTP app. This supports Compose file secrets that retain their host ownership. The HTTP app runs as an unprivileged OS user. PostgreSQL persists in the Compose project volume `miracle_postgres-data`; rebuilds do not reset it. Apply migrations on app startup; before upgrading, take and verify a backup. Use a versioned image digest/release artifact for repeatable production rollbacks.
5. Bootstrap the first administrator inside the app container using its compiled CLI, with credentials from a protected environment/stdin: `node dist/server/server/cli.js bootstrap-admin`. Use `docker compose exec app sh` and the CLI prompt; do not put a password in command arguments. Confirm `/api/health`, login, a read-only connection and a successful query through HTTPS.

Do not run `docker compose down -v` on a persistent installation. `docker compose stop app` or `docker compose down` preserves named volumes. The test engines are started only with `--profile test`; the app is started only with `--profile app`.

After building the image, run `scripts/smoke-image.sh` while the project PostgreSQL service is running. It starts the production image on the project network without publishing a host port, uses a disposable database and the protected key file, checks health and a built frontend asset, verifies the HTTP process runs as UID 1000, and removes only its temporary container/database/env file. It does not share the active application database. If needed set `MIRACLE_SMOKE_IMAGE` to a particular built release tag.

## Backups, restore and rollback

Run `scripts/backup.sh` from the repository root. It writes a mode-0600 custom-format PostgreSQL dump under `.local/backups`. This includes board-referenced snapshots. Store an encrypted off-host copy and separately protect the matching encryption key and deployment env. A DB dump without the key cannot recover connection credentials. Set backup frequency and retention to your required RPO; monitor backup age and storage capacity.

Run `scripts/restore-rehearsal.sh .local/backups/FILE.dump`. It creates a uniquely named disposable database in the project PostgreSQL instance, restores with `--exit-on-error`, lists restored table count, and deletes only that rehearsal database on exit. This checks restore mechanics without replacing application state. For a complete disaster rehearsal also launch a separate application against the restored database with the backed-up key and verify login, board snapshot retrieval and a test connection. Record duration to establish the actual RTO; this repository does not claim a measured production RPO/RTO.

For actual recovery, stop application writes, restore into a new empty database using `pg_restore --exit-on-error --no-owner`, set `DATABASE_URL` to it, supply the matching key and restart the app. Validate before routing users back. Preserve the old database until acceptance. A code rollback must use a database schema compatible with the earlier version; never restore an old dump over newer user work as a routine code rollback.

## Limits and monitoring

Defaults: query timeout 120 seconds, 50,000 rows, 20 MiB per result, 2 concurrent runs per user, 4 global, 5,000 chart points, 2 GiB stored results. Environment overrides: `QUERY_TIMEOUT_MS`, `MAX_RESULT_ROWS`, `MAX_RESULT_BYTES`, `MAX_USER_RUNS`, `MAX_GLOBAL_RUNS`, `RESULT_QUOTA_BYTES`. Tune with actual engine and workload measurements. Durable board-referenced results survive cleanup; unreferenced results expire after 24 hours and query history after 30 days. Track disk usage, query failures/timeouts and database health. No realtime collaboration is claimed: board saves use optimistic revisions and conflicts require reload or copy.
