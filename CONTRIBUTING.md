# Участие в Miracle

Для ошибки укажите версию, ОС, архитектуру и шаги воспроизведения. Примеры SQL и данные должны быть синтетическими. Об уязвимостях сообщайте по [политике безопасности](SECURITY.md).

## Локальный запуск

Нужны Node.js 24 и npm. PostgreSQL и Docker для разработки приложения не требуются:

```sh
npm ci
MIRACLE_DATA_DIR=.local/workspace APP_ORIGIN=http://127.0.0.1:5178 npm run dev
```

Интерфейс: `http://127.0.0.1:5178`, API разработки: порт 3001. `APP_ORIGIN` задаёт адрес интерфейса для Vite proxy. На Windows работайте в терминале WSL 2. Альтернативные настройки — [.env.example](.env.example).

Производственный CLI выбирает свободный порт ОС; `--port` или `PORT` фиксирует его. Текущая папка запуска становится проектом, `--project-dir` задаёт другую папку. По умолчанию данные и ключ находятся в `PROJECT/.miracle/`; `--data-dir` / `MIRACLE_DATA_DIR` меняет только хранение. Повторный запуск проекта переиспользует процесс, разные проекты имеют отдельные порты. Для локального исходного CLI: `npx tsx src/server/cli.ts start --project-dir /path/to/project`.

Не путайте проектные файлы, SQLite и глобальную установку: код, реестр, журналы и локальные разрешения профилей лежат в установке; документы редактора и чаты — в базе проекта. Резервные копии не содержат обычные файлы проекта или provider home. Новые данные используют схему SQLite 4; миграции с 1–3 должны сохранять UUID, ключ, подключения и результаты. Следующая неподдерживаемая версия схемы в фикстуре — 5.

Не публикуйте .local, .miracle, ключи, сертификаты, резервные копии или личные данные. Сохраняйте SQLite и соответствующий ключ вместе.

## Проверки

```sh
npm test
npm run build
```

API-тесты используют временные SQLite-каталоги. Для локальных TLS-фикстур и subprocess-тестов нужен доступ к локальным сокетам.

Адаптеры Codex и Claude используют нативные структурированные протоколы. Тестируйте реальные подпроцессы с фикстурами: Unicode и частичные сообщения, разрешения, отмена, восстановление сессии, завершение owned process group. Не заменяйте эти проверки mock-ответом адаптера. Команды профилей не исполняются через shell; сложные оболочки оформляются executable wrapper. Сохраняйте пользовательские модель/разрешения и показывайте фактическую производную команду без секретов.

Реальный smoke каждого CLI проверяется отдельно с синтетическим проектом: файл → SQL → результат → доска, фон, переподключение, продолжение и отмена. Авторизуйте провайдер штатно до теста; не копируйте provider home в фикстуры и репозиторий. Наличие зелёного протокольного теста не подтверждает реальный Claude: если CLI недоступен, явно укажите непроверенный сквозной сценарий. Отдельно проверяйте два проекта, портовые cookies, alias, конфликт порта, изоляцию MCP-токенов и перенос профилей без доверия к исполняемой команде.

Реальные ClickHouse/Trino проверяются отдельно. При наличии Docker можно запустить только тестовые аналитические источники:

```sh
docker compose --profile test up -d --wait clickhouse trino
npm run test:integration
npx tsx tests/clickhouse-tls-integration.ts
```

Эти контейнеры — инструменты разработчика, не часть пользовательской установки. Используйте синтетические данные и не останавливайте чужие сервисы. Конфигурация HTTPS/mTLS находится в infra и integration-скриптах.

Проверки сборки и установщиков описаны в [releasing.md](docs/releasing.md). При изменении зависимостей обновите package-lock.json и `npm run notices`.

## Pull request

1. Опишите проблему и итоговое поведение.
2. Добавьте проверку пользовательского сценария; для текста достаточно проверить ссылки и команды.
3. Укажите пройденные проверки и ограничения среды.
4. Выполните `git diff --check` и обновите документацию.
5. Для UI приложите пример с синтетическими данными.

Не изменяйте постоянные рабочие области ради теста. Проект распространяется по [Apache-2.0](LICENSE).
